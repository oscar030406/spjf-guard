READING: time_cost is the SUM over the problem's test cases of each test's
measured execution time, each TEST capped at the problem's time limit.  It is
per-test execution time aggregated per submission, NOT judge occupancy: it
excludes compilation, container start-up, fixture copying and result write-back,
which is why 8.53% of judged rows record exactly 0 ms (CE and other rows that
never ran a test).
EVIDENCE  (i) time_cost equals the sum of the per-test ms on 0.9998 of the rows that
  carry a per-test table and the max on only 0.0524; (ii) memory_cost equals the
  per-test MAX on 0.9999, so the two fields aggregate the same per-test
  measurements with different operators, which one wall-clock occupancy number
  could not do; (iii) on TLE rows the per-test max equals the time limit exactly
  on 0.7130 of them, so the cap is applied per test, and time_cost can reach
  n_tests * time_limit, which is what the observed maximum does.
CONFIDENCE high for 'sum of per-test measured run times, per-test capped'.
  Whether each per-test number is CPU time or sandbox wall clock is NOT decidable
  from this dump (no timestamps, no second clock).  The service-time model
  therefore adds an explicit constant for the parts of judge occupancy the field
  does not contain; that constant is an assumption and a sensitivity with a
  per-test term is run.  Contrast with CodeBench, where C is wall-clock judge
  occupancy including interpreter start-up (codebench_semantics, medium
  confidence).  The two platforms measure different things, and the paper must
  say so rather than putting the two distributions on one axis.

--- A. what the cost variable is ---
CodeBench  C = wall-clock judge occupancy of one submission, interpreter
           start-up included (medium confidence, codebench_semantics);
           platform limit L = 60 s; C_cap = min(C, 60).
ACcoding   time_cost = SUM over the problem's test cases of each test's measured
           execution time, each TEST capped at the problem's time limit (high
           confidence, audit 1e).  Compilation, container start-up and result
           write-back are NOT in it, so the service model has to add them:
           C = 0.5 s + time_cost/1000, giving L = 30.5 s.
AGREE      both are heavy-tailed positive costs with a hard per-submission
           ceiling, and on both the ceiling is enforced by the platform.
DIFFER     one measures occupancy, the other execution.  Waiting times in
           seconds are therefore not comparable across the two platforms; gain
           ratios and orderings are.  The 0.5 s constant is an assumption of
           this precheck, not a measurement, and section B shows how much of
           the tail shape it decides.
