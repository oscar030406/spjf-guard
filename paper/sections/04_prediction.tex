\section{Cost Prediction}
\label{sec:prediction}

The scheduler needs, for every arriving job, a number that says how long the job will run,
computed from history alone. Users and tasks form a graph, because many users attempt the
same task and each user attempts many tasks. A natural question is therefore whether a
model that reads this graph predicts better than one that reads each job's own history.
This section compares three kinds of model on the two grading logs of
Section~\ref{sec:data} and chooses the one the scheduler uses.

\subsection{Targets and Measures}

For ranking, the target is the conditional mean $\mathbb{E}[C_i \mid x_i]$. This mean
orders a batch optimally on one server, by the pairwise-interchange argument of
Section~\ref{sec:rank}. The mix of jobs shifts between periods, so to compare predictors
across periods we also score each model on a binary label. A job is \emph{heavy} when its
cost exceeds the 95th percentile of the training rows. On the main grading log this cut-off
is \devnum{1.559} s, and heavy jobs are \devnum{1.31\%} of the test period against
\devnum{5.00\%} of the training period. On the second log the cut-off is \devnum{1{,}314}
ms and heavy jobs are \devnum{5.07\%}. For the heavy label we report the area under the
receiver operating characteristic curve (AUROC). For the predicted cost we report the root
mean squared error (RMSE) of $\log(1+C)$ and the Spearman rank correlation, since a ranking
policy uses the order of the scores and not their level.

\subsection{Protocol}
\label{sec:pred_visibility}

Every model sees the same rows, the same split into training and test periods, and the
same visibility rule~\eqref{eq:visibility}. Historical features are computed by streaming
the log in the order in which results became available and reading each user's and each
task's state at the query instant. Recomputing these features from scratch gives
\devnum{0} disagreeing rows in all eight configurations we tested. Each test period is
predicted by a model fitted only on earlier periods and frozen before the period's first
arrival, and the heavy cut-off is refitted on that model's own training rows. Delaying the results by up to ten minutes
before they may enter the features leaves the ranking intact and worsens only the
calibration. Supplementary Section~S1 gives these audits.

The three kinds of model are listed in Table~\ref{tab:predictors}.
\begin{itemize}
  \item Gradient-boosted trees \cite{ke2017lightgbm} over five feature groups, namely the
  task's history (M1), the user's history (M2), static features of the submitted code (M3), all
  of these together (M4), and M4 with one-hop aggregates over related users and tasks
  (M5).
  \item A GRU over the user's earlier jobs, used alone (R1) and as a
  state vector added to M4's features inside the trees (R1S).
  \item A heterogeneous GNN of the R-GCN type \cite{schlichtkrull2018rgcn}, over users, tasks, the assignments
  that group tasks and the class cohorts that group users. It is tested as a ladder of
  five models. The first is a multilayer perceptron on M4's features (N0). The others are
  the graph architecture with every neighbour set empty and no group nodes (G0U), with the
  group nodes but no edges (G0), with the real edges (G1), and with the edges shuffled
  within each period (G2). G2 keeps each node's
  number of neighbours and changes only who they are, so if the edges carry information,
  G2 must lose it.
\end{itemize}

\subsection{What the Comparison Shows}
\label{sec:pred_comparison}

The graph does not help on average. One-hop aggregates barely change the trees' AUROC,
since M5 $-$ M4 is \devnum{$+0.0019$} of AUROC on the main log and \devnum{$-0.0002$} on
the second. In the GNN ladder, removing every edge (G0) or shuffling them (G2) leaves AUROC
within \devnum{0.002} of G1. The paired intervals for G1 $-$ G0,
\devnum{$-0.0001$ $[-0.0019, 0.0018]$}, and for G1 $-$ G2, \devnum{$+0.0019$ $[-0.0000,
0.0042]$}, both contain zero. The one step in the ladder that matters is N0 to G0U,
\devnum{$+0.0139$ $[+0.0090, +0.0195]$} of AUROC, and this step changes the encoder while
the edges stay empty.

The edges help only for tasks with little history of their own. On the \devnum{1{,}092}
test rows whose task has fewer than five visible earlier results, G1 beats M4 by
\devnum{$+0.1464$ $[+0.0997, +0.1887]$} in Spearman correlation. On these rows G1 also beats
its own shuffled-edge control by \devnum{$+0.0282$ $[+0.0130, +0.0432]$}, whereas over all
rows G1 $-$ G2 is \devnum{$+0.0063$ $[+0.0014, +0.0111]$}. We read this as a property of
the task and not of relational models. When each user and each task already has a rich
record, a neighbourhood adds little except for an entity with no record yet.

% sloppypar: the unbreakable interval below otherwise overruns the margin by about 10 pt.
\begin{sloppypar}
Prediction scores and queueing outcomes do not rank the models the same way. R1S has the
highest AUROC, \devnum{0.9366}. Its difference from M4's \devnum{0.9283} is
\devnum{$+0.0083$ $[+0.0038, +0.0131]$}. In the queue, however, R1S gains
\devnum{$+0.007$ $[0.003, 0.011]$} of the gap at utilisation \devnum{0.8}, loses
\devnum{$-0.010$ $[-0.022, -0.002]$} at \devnum{0.5}, and is unresolved at \devnum{1.0}
(Section~\ref{sec:overlay} defines the three loads). M5 has the higher AUROC of the two full
tree models, and M5 loses in the queue at all three loads, by \devnum{0.012},
\devnum{0.008} and \devnum{0.010} of the gap, each interval excluding zero. The scheduler
therefore uses M4, chosen on the queueing outcome of validation periods rather than on
prediction scores.
\end{sloppypar}

Which history matters varies by platform. The user's history leads on the main log, and the
task's history leads on the second by \devnum{0.11} of AUROC (Supplementary Table~S2).
Supplementary Section~S1.2 compares the feature groups on the four logs from outside
education.

Prediction is cheap next to the queue. The median job on the main log runs for
\devnum{204} ms, and charging each model's measured cost per job to the predictive
policies changes the gap closed by less than \devnum{0.001} at every load (Supplementary
Section~S1).
