# 0006 单机轨迹的拷贝数在开发池上选定，封存池沿用并如实报告利用率

日期 2026-09-21。

## 决定

k = 1 那条轨迹由若干份班次—学期拷贝叠加而成，拷贝数怎么定是一个设计值。原来的定法是探针：
一份份加，直到一台评测机上最忙那小时的利用率落进 `[0.78, 0.82]`，取最靠近 0.80 的那个状态
（`single_server_pool`，`configs/main.yaml` 的 `overlay.single_server`）。在 `primary` 上它
选出 **321** 份，忙时利用率 0.8000。

从现在起：

- 探针只在它当初选的那个池（`overlay.single_server.pool`，即 `primary`）上跑，行为一字未改；
  选出的份数与配置里钉的 `copies: 321` 不一致时，脚本在开头打印一行不一致提示，和主运行对选参
  的处理一样。
- 换到别的池（封存池就是其中之一）时，**沿用 321 这个数**，按同一个种子抽出的候选序列取前 321
  份，全程不看利用率；实际达到多少就报多少（`single_server_copies`）。

## 为什么

在封存池上重跑探针，等于用封存数据决定一个设计值：份数由"封存学期上哪一档利用率最接近 0.80"
选出来，而那条信息要到封存学期打开之后才有。这正是冻结要挡的那件事——`docs/sealed_run_procedure.md`
里"封存学期上实际达到的利用率如实报告，不回头调 k 去凑目标值"说的是同一条纪律，只是那句话针对
的是 k，这里针对的是拷贝数。

反过来，把开发池选出的份数搬过去，代价是封存池的忙时利用率可能不落在 0.80 附近。这个代价是可以
承受的，而且是可读的：表里同时印出实际利用率，读者能自己判断两条轨迹的负载差多少。相反，为了让
利用率对齐而在封存池上重选份数，会让"参数在冻结前全部定死"这句话对单机轨迹不成立。

另一个可以考虑的做法是把开发池选中的那 321 个 (班次—学期, 周偏移) 二元组原样搬到封存池。做不到：
那些班次—学期是开发学期的，封存池里根本没有同名的对象。能搬过去的只有份数和抽取规则。

## 代价

- 封存池的 k = 1 轨迹落在哪个利用率上，冻结时不知道。若它离 0.80 很远，那条轨迹与多机表的负载
  不可比，论文要按实际值说，不能说成"同一档负载"。
- 封存池的班次—学期比开发池少（三个学期对六个），要凑够 321 份就得把名单多列几遍：列几遍由
  份数除以班次—学期数决定，不是另选的参数。份数少的池里会出现同一个 (班次—学期, 周偏移) 被叠
  两次，这和多机叠加里本来就允许的重复是同一件事。冻结的是份数，不是拷贝的多样性。
- 两条 k = 1 轨迹从此各有各的文件名（`k1_rep0.npz` 与 `sealed_k1_rep0.npz`）和各自的产物清单
  （`run.sealed_k1_tables`），否则封存那一次会盖掉开发期的输入，而开发期的表是按那份输入的哈希
  记在清单里的。

## 没有改的

探针本身、利用率窗口、目标 0.80、种子与偏移（`seed * 100 + 50`）、`primary` 上选出的 321 份，
以及由此产生的 `outputs/dev_tables/k1/` 全部数字。
