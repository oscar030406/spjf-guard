# 0002 到达与可见性按结果可用时刻定义，同秒记录用确定性抖动打散

CodeBench 的 `SUBMITION` 事件头记的是哪一刻，日志里没写。2026-09-19 的字段语义检验（`prechecks/codebench_semantics/`）指向「结果写入时刻」：2020–2022 年执行时间 5–60 秒的提交，距同一学生上一次执行的间隔随 `C` 一比一增长（斜率 0.99），距下一次几乎不变（斜率 0.16）；学生手动终止长运行后反馈事件在约 0.1 秒内出现，与 `C` 无关。2018–2019 年 1–10 秒的运行两种读法都不贴合。

我们把主解释定为 `arrival = t - C`、`done = t`，历史特征的可见性写成 `done_j + delta <= a_i`，并把旧解释（`arrival = t`、`done = t + C`）保留为敏感性，两套数字分开列、不混用。理由是：调度仿真里「一个 job 什么时候进队」和「它的结果什么时候能被后面的 job 看到」是两个不同的量，而证据支持的是事件头等于后者。把它当成前者会让每个 job 的到达系统性地晚 `C` 秒，重任务晚得最多，恰好是排队结论最敏感的地方。

事件头只记到秒，同一秒里常有多条记录，先后无从判断。我们不按行号定序——行号取决于解析顺序——而是给每条记录加一个由它的稳定 id（semester, class, user, assessment, exercise, blk_i）和固定 key `cbjitter20260919` 算出的 `u ∈ [0,1)` 抖动，`ts' = ts + u`。这样同秒记录的先后在任何机器、任何一次运行里都一样，而且和输入行序无关。换 key 会改变每一个到达，属于协议变更，所以 key 写进配置并进配置锁。
