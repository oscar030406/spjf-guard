# 0002 Arrival and visibility are defined by the time the result became available; records in the same second are separated by a deterministic jitter

The logs do not say which moment the `SUBMITION` event header of CodeBench records. The field-semantics check of 2026-09-19 (`prechecks/codebench_semantics/`) points to "the time the result was written": for 2020–2022 submissions with execution times of 5–60 seconds, the gap to the same student's previous execution grows one for one with `C` (slope 0.99), while the gap to the next one hardly changes (slope 0.16); after a student manually stops a long run, the feedback event appears within about 0.1 seconds, independent of `C`. For 1–10 second runs in 2018–2019, neither reading fits.

We set the primary interpretation to `arrival = t - C`, `done = t`, write the visibility of history features as `done_j + delta <= a_i`, and keep the old interpretation (`arrival = t`, `done = t + C`) as a sensitivity analysis; the two sets of numbers are listed separately and never mixed. The reason: in a scheduling simulation, "when a job enters the queue" and "when its result can be seen by later jobs" are two different quantities, and the evidence supports the event header being the latter. Treating it as the former would make every job's arrival systematically `C` seconds late, and heavy jobs the latest, which is exactly where the queueing conclusions are most sensitive.

The event header is recorded only to the second, and there are often several records in the same second whose order cannot be determined. We do not order them by line number, which depends on parsing order. Instead each record gets a jitter `u ∈ [0,1)` computed from its stable id (semester, class, user, assessment, exercise, blk_i) and the fixed key `cbjitter20260919`, and `ts' = ts + u`. The order of same-second records is then the same on every machine and in every run, and does not depend on the input line order. Changing the key changes every arrival and counts as a protocol change, so the key is written into the configuration and covered by the protocol lock.
